# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**ThingsAlive NeoX** — a React 18 + Vite + Supabase ERP application (package name: `procurepro`, v3.0.0). Manages expenses, procurement, HR, projects, tasks, timesheets, chat, and AI-powered requirement analysis for a single organisation.

## Commands

```bash
npm run dev       # start Vite dev server
npm run build     # production build → dist/
npm run preview   # preview the production build
```

There are no lint or test scripts. The build (`npm run build`) is the primary correctness check — run it after significant changes to verify no JSX/import errors.

## Environment Variables

Vite only loads `.env`, `.env.local`, `.env.[mode]`, `.env.[mode].local`. The file `prod.env` is **not** loaded automatically and is kept only as a reference for the production Supabase project.

Required keys in `.env`:
```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
VITE_DEEPSEEK_API_KEY      # DeepSeek V3 for Neo Task AI
VITE_GEMINI_API_KEY        # Gemini 2.5 Pro for Neo Task AI
VITE_TURNSTILE_SITE_KEY    # Cloudflare Turnstile site key (public) for the /l/:slug public lead-capture form
```

The Turnstile *secret* key is never an env var — it's stored server-side only, set write-only from Settings → Sales Config → Landing Links (`set_turnstile_secret` RPC, STEP75), readable by nothing except the `public_submit_lead` SECURITY DEFINER function.

## Database

All schema changes are SQL files in `sql/` numbered by step (STEP20–STEP24b). Run them in the Supabase SQL Editor in order. After creating new tables always end the script with `NOTIFY pgrst, 'reload schema';` to clear the PostgREST schema cache (avoids PGRST205 errors).

**Important:** Use soft FK references (plain `UUID` columns) when referencing tables that may not exist yet (`user_stories`, `project_tasks`). Hard `REFERENCES` constraints silently abort the entire script if the target table has an unexpected structure.

When dropping and recreating tables with RLS policies, use `DROP TABLE IF EXISTS ... CASCADE` — do **not** use standalone `DROP POLICY IF EXISTS` statements before the table exists, as the `IF EXISTS` guard on `DROP POLICY` only covers the policy name, not the table.

## Architecture

### Routing & Auth (`src/App.jsx`)

All routes inside `<Layout>` are protected. Auth state comes from `useAuth()`. Route-level access is checked with role helpers:

```js
const isAdmin    = ['admin','ceo'].includes(role)
const isManager  = ['admin','ceo','manager','department_head'].includes(role)
const isFinance  = ['admin','ceo','finance'].includes(role)
const isHR       = ['admin','ceo','hr'].includes(role)
```

Unauthenticated users are redirected to `/auth`.

### Auth Context (`src/context/AuthContext.jsx`)

`useAuth()` returns `{ user, profile, loading, signIn, signUp, signOut, refreshProfile }`. Profile loading retries up to 7 times with exponential backoff (700ms × attempt) to handle Supabase eventual-consistency delays. The `profile` object includes a joined `dept` (department name/code).

### Tab Visibility (`src/context/TabVisibilityContext.jsx`)

Controls which sidebar tabs each role can see. `isTabVisible(tab)` is the gating function — Supabase-backed (`modules` for a company-wide enable/disable kill switch, `module_role_visibility` for per-role visibility, default visible unless a row says otherwise), org-wide and shared across every browser/device. admin/ceo always bypass the per-role check (never the kill switch). Edited from Settings → "Roles & Modules" (`RolesModulesTab` in `SettingsPage.jsx`), backed by `src/lib/modules.js`. This is the **only** place nav visibility is gated — `Layout.jsx`'s `ALL_NAV` has no per-item role list of its own (removed; previously duplicated/conflicted with this table — see `sql/STEP112_nav_role_visibility_seed.sql`). Every new page route must still be registered in `ALL_NAV` with a matching module key in `src/config/modules.js` so it can be toggled here. A second, additive gate is the Workspace module list (`workspace_profiles.enabled_module_keys`), checked via `isModuleInWorkspace()` in `src/lib/workspace.js`: saves also record `known_module_keys` (STEP236), so a module added later shows by default instead of being hidden.

### Layout & Navigation (`src/components/layout/Layout.jsx`)

Single shell with collapsible sidebar (`ALL_NAV` array) and topbar. Records a `page_view` event to `app_events` on every route change using a module-level `SESSION_ID`. Nav item visibility is entirely `isTabVisible()`-driven (see Tab Visibility above) — `platformOnly` is the one exception, gated on `profile.is_super_admin` instead, above any per-org module system.

### Data Fetching Pattern

No React Query is used in practice. All data fetching is direct Supabase client calls inside `useEffect`:

```js
const { data, error } = await supabase.from('table').select('*').eq('field', value)
```

Real-time subscriptions use `supabase.channel(...).on('postgres_changes', ...).subscribe()`. Always unsubscribe in the `useEffect` cleanup. Store the channel in a `useRef` to avoid stale-closure issues in subscription callbacks.

### Supabase fallback route (`src/lib/supabase.js`, `netlify.toml`, `vite.config.js`)

Some ISPs / networks block `*.supabase.co`. The client's `global.fetch` (`routedFetch`) calls Supabase directly first and, on a network-level failure, retries through this site's own `/sb/*` proxy (Netlify redirect, status 200; Vite dev proxy mirrors it) and stays on it for 6 hours (`localStorage['neox.supabaseRoute']`). Storage `getPublicUrl` / `createSignedUrl(s)` results are rewritten too (`routeUrl()`); realtime websockets always go direct. Keep the `/sb/*` rule above the SPA fallback in BOTH `public/_redirects` (Netlify reads it before `netlify.toml`) and `netlify.toml`. `VITE_SUPABASE_PROXY=off` disables it.

### Utility Functions (`src/lib/supabase.js`)

Centralised helpers used across all pages:
- `rupee(n)` / `rupeeFull(n)` — INR formatting (en-IN locale)
- `dateFmt(d)` / `timeFmt(d)` — "DD MMM YYYY" / "DD MMM HH:mm"
- `nextNum(type)` — sequence numbers (EXP, TRV, PR, PO, INV, AST) via RPC with fallback

### Approval Flow (`src/lib/approvalFlow.js`)

Multi-step approval chains defined per submitter role. Status progression: `submitted → manager_review → ceo_review → finance_review → approved`. Chain definitions live in `CHAINS` keyed by role.

### Notification System

- `src/lib/notifications.js` — `sendNotif(recipientId, opts)`, `sendNotifToMany()`, `notifyManagers(opts)`
- `src/context/NotificationContext.jsx` — subscribes to realtime INSERT/UPDATE on `notifications` table; exposes `unreadCount`, `markRead`, `markAllRead`
- Bell icon turns yellow with glow when `unreadCount > 0`

### Neo Task AI (`src/pages/NeoTaskAIPage.jsx` + `src/lib/llm.js`)

AI-powered requirement analysis. Upload a document → AI generates stories, backlog, tasks, test cases, APIs, sprint plan.

`src/lib/llm.js` is the unified LLM service:
- `LLM_MODELS` registry — DeepSeek V3 (`deepseek-chat`) and Gemini 2.5 Pro (`gemini-2.5-pro`)
- `analyzeRequirements(sessionId, modelId)` — routes to `callDeepSeek()` or `callGemini()`
- Gemini uses the OpenAI-compatible endpoint: `https://generativelanguage.googleapis.com/v1beta/openai/chat/completions` with model `gemini-2.5-pro` (not the dated preview slug)
- `parseJSON()` — 3-strategy robust parser (direct → code block → brace extraction)
- Results persisted to 6 tables: `ai_analysis_sessions`, `ai_generated_stories`, `ai_generated_backlog`, `ai_generated_tasks`, `ai_generated_test_cases`, `ai_generated_apis`

### Sales & Pre-Sales CRM (`sql/STEP68`–`STEP75`, `src/lib/sales*.js`, `src/pages/{Leads,Opportunities,SalesTasks,ProductLaunches,Tenders,PilotProjects,BootstrapPrograms,SalesTimeline,SalesDashboard}Page.jsx`)

Lightweight CRM: every entry track (Lead, Won Tender, Converted Pilot, Converted Bootstrap Program) converges into `sales_opportunities`, which feeds the **existing** Proposal Builder via `salesOpportunities.convertToProposal()` (calls `proposals.js`'s `createProposal()` — never duplicates proposal/cost logic) and the **existing** actual-profit engine via `salesFinance.recomputeSalesProfitAttribution()` (reads `profit_margins`, computed by `profitMargin.js`'s `recomputeMargin()` — never recomputes cost itself). Pipeline stages, regions, roles, lookup lists, assignment rules and stale/overdue thresholds are all admin-configurable from Settings → "Sales Config" tab (`SalesConfigTab` in `SettingsPage.jsx`), backed by `src/lib/salesAdmin.js`.

RLS convention for this module: permissive SELECT + role-gated writes (matches the rest of the app) EXCEPT `sales_profit_attribution`, which is deliberately DB-restricted to admin/ceo/finance/sales_head — a rep's own booked-vs-delivered gap isn't shown to them by default (config flag `view_sales_profit_attribution_individual` in `sales_config_flags` can loosen this later).

**Public lead capture** (`STEP75`, `src/pages/PublicLeadFormPage.jsx`, route `/l/:slug`): admin creates a named "Landing Link" (Settings → Sales Config → Landing Links) locked to a domain/region/source, gets a shareable external URL. The public page is unauthenticated and standalone (no `Layout`, handled by a `location.pathname.startsWith('/l/')` short-circuit in `App.jsx` before the auth branch). It never touches tables directly — both reads and writes go through `SECURITY DEFINER` Postgres RPCs (`get_landing_link_public`, `public_submit_lead`) that anon is granted `EXECUTE` on but no table access. `public_submit_lead()` verifies a Cloudflare Turnstile token server-side (via the `http` Postgres extension, secret stored write-only in `sales_public_form_secrets` — no SELECT policy exists on that table at all) before running the same auto-assignment logic as `salesLeads.createLead()` and inserting the row. Requires `VITE_TURNSTILE_SITE_KEY` in `.env` (public) and the secret key set once via the Settings UI (never an env var).

Replaces the manual `IoT_Daily_Support_Tracker.xlsx`. ### Outlook email → project action items (`sql/STEP261`–`STEP262`, `supabase/functions/outlook-*`, `_shared/outlook*.js`)

Customer emails in a Microsoft 365 mailbox that report a project issue become `project_tasks` under the matched project. Flow: Graph change notification → Edge Function `outlook-webhook` (echoes `validationToken`, checks the mailbox's secret `clientState` constant-time, records the message id via `outlook_enqueue_message`, returns 202, nudges the worker) → `outlook_email_messages` (PENDING; unique per mailbox + Graph immutable id, and per internetMessageId) → Edge Function `outlook-sync` (cron every minute with `CRON_SECRET`, or a signed-in user for test/subscribe/reconcile/process): `outlook_claim_messages` (SKIP LOCKED, stale lock reclaim 10 min) → Graph fetch (plain-text body, `Prefer: IdType="ImmutableId"`) → pre-filter (auto-replies, newsletters, spam, no-reply) → classify (Claude / DeepSeek / Gemini via the org's `llm_settings`, else keyword rules; email fenced as untrusted data, output clamped by `sanitizeClassification`, prompt-injection → review) → match project (code → same conversation → name → sender's customer via `contacts` / `customers` email or company domain; a code belonging to another customer, several matches, closed projects or no match → REVIEW; never creates projects) → `outlook_create_task` (one transaction: row lock, `INSERT … ON CONFLICT (source_email_id)`, link, notify, audit — `project_tasks.source_email_id` is UNIQUE, so retries / duplicate notifications can't make a second task). Failures: `outlook_record_result('FAILED')` → backoff 1, 2, 4 … min (≤ 6 h) or Graph's Retry-After, DEAD after 6 attempts. Subscriptions (inbox `created`, ~70 h) are created / renewed (< 24 h left; 404 → recreate) / removed by the worker; lifecycle events (reauthorizationRequired / subscriptionRemoved / missed) are flagged for it; inbox delta every 15 min recovers missed mail (`delta_link`, only mail since `process_since`). Secrets: `outlook_mailbox_secrets` (client secret + clientState, RLS with no policies; set via `outlook_set_client_secret`), env fallbacks `MS_GRAPH_TENANT_ID/CLIENT_ID/CLIENT_SECRET` — see `supabase/outlook.env.example`. Retention: `outlook_prune_email_data()` (daily cron) clears body text after `retention_days`. Pure logic is in `supabase/functions/_shared/outlook{Graph,Classifier,Matcher,Processor,Webhook}.js` (import-free, also imported by the web app) — run `node --test src/lib/outlookEmail.test.mjs` after changing it. UI: page **NeoX Email Intelligence** (formerly Email to Tasks; route still `/email-to-tasks`, managers: review queue with "Create action item", created, all, failed + retry, audit log, settings) and Settings → **Outlook Email** (`OutlookSettings.jsx`, admin/ceo edit). **Outlook Email** tab (`/outlook-inbox`, below Chat, STEP262): every email in the mailbox with an internal-only reply thread (`outlook_email_notes`, never sent to the customer; notifies earlier repliers + the task assignee; realtime). Who can open it = `outlook_mailboxes.inbox_roles` (default admin/ceo/manager/department_head); mailbox connection details stay admin/manager-only (inbox readers get names via `outlook_inbox_mailboxes()`).

### Email Intelligence — configurable classification, documents, PO/GRN/invoice intake (`sql/STEP263`–`STEP265`, `_shared/ei*.js`)

Runs inside `outlook-sync` before the STEP261 project-issue flow whenever the org has a published configuration (no config = STEP261 behaviour only). **All business configuration is data**: `ei_email_categories` (intent, workflow handler `AP_INVOICE | PROJECT_ISSUE_TASK | REVIEW_QUEUE | VENDOR_VERIFICATION | RECORD_ONLY | IGNORE`, review role, threshold, related document types), `ei_keyword_rules` (terms, ANY/ALL, locations SUBJECT/BODY/SENDER/SENDER_DOMAIN/ATTACHMENT_NAME/ATTACHMENT_TEXT, PHRASE/WORD/PARTIAL/REGEX with a nested-quantifier guard in SQL + JS, exclusions, vendor scope, weight, effective dates), `ei_document_types` (formats, extraction schema `fields` with optional regex patterns, required fields, destination `INVOICE_REGISTER | CREDIT_NOTE_REVIEW | REVIEW_QUEUE | NONE`), `ei_vendor_aliases` (point at the EXISTING vendor master; email/domain aliases count only when verified), `ei_settings` (tolerances, require PO / receipt, auto-create, confidence bands, AI toggles, attachment limits, `scoring.document_evidence_weight`). Defaults (38 categories, 32 document types, ~41 rules) are seeded per org by `ei_seed_defaults()` as editable rows. **Versioning:** edits are a draft; `ei_publish_config()` validates and snapshots into `ei_config_versions` (immutable); the worker uses the latest version (`ei_active_config`) and stamps it on every email / attachment / exception; `ei_rollback_config(n)` restores tables from version n and publishes it as a new version; `ei_config_audit` logs every change (triggers; seeding/rollback log one row). Admin/ceo/finance edit, managers read. **Pipeline** (`eiPipeline.js`, every side effect injected): attachments listed + downloaded from Graph (`listAttachments`, `attachmentBytes`), size/type limits, SHA-256, stored in the PRIVATE bucket `email-attachments/<org>/<message>/…`, text read in Deno (`eiText.ts`: unpdf for PDF text, SheetJS for sheets; scanned PDFs/images only via AI — Claude reads PDFs/images natively) → each file classified on its own from its own name/text (never the email text) → intents from keywords + document evidence + optional AI (`eiAI.js`, codes validated against config, email/document fenced as untrusted) → per invoice-like document: pattern + AI extraction, validations (required fields, arithmetic, GSTIN check digit, AI-vs-text conflicts), vendor (GSTIN → email → domain → name; GSTIN-vs-sender disagreement = CONFLICT), PO by number, receipts summed across GRNs, amounts vs received value / PO balance across all invoices on the PO, duplicates (vendor + number, file hash) → `decideInvoice()` → `ei_create_invoice()` (the only automated writer to `invoices`: row lock, ownership + duplicate re-check under an advisory lock, `UNIQUE(source_attachment_id)`, status `uploaded` — nothing approved/posted/paid) or typed `ei_exceptions` (one OPEN row per item + kind; kinds VENDOR_VERIFICATION, PENDING_PO, PENDING_RECEIPT, DUPLICATE_REVIEW, REVISED_INVOICE, INVOICE_MISMATCH, DATA_VALIDATION, CREDIT_NOTE, CLASSIFICATION_REVIEW, DOCUMENT_REVIEW, BANK_DETAIL_CHANGE, VENDOR_MASTER_CHANGE, `CATEGORY_REVIEW:<code>`). Bank/vendor-master change intents always raise a verification item (primary or secondary) and are never applied; closing them needs admin/ceo/finance. Email status `PROCESSED` + `intents` + `config_version`. Reviewers: `ei_resolve_exception` (note required), `ei_assign_exception`, `ei_review_create_invoice` (admin/ceo/finance, reason required). `outlook-sync` action `dry_run` = read-only test of the DRAFT config (Settings → Email Intelligence → Test). UI: `src/components/ei/` (EmailIntelligenceSettings = configuration centre, EiTester, ExceptionQueue + DocumentQueue), NeoX Email Intelligence tabs Exceptions / Documents / Configuration; InvoicesPage shows "Received by email" for `source_attachment_id` invoices. Finance is now an Outlook viewer (`_outlook_can_view`, STEP265). Tests: `node --test src/lib/emailIntelligence.test.mjs` (reads the STEP264 extraction schema itself). Not built yet: visual workflow builder, approval matrix / SLA / escalation engine, notification templates, Vendor 360 / Project 360, management dashboard, Gmail, line-item and multi-project allocation, OCR without an AI provider, DOCX text, ZIP.

### Email Intelligence — document register, taxonomy, versions, compliance (`sql/STEP268`–`STEP272`, `_shared/ei{Documents,Taxonomy,TaxonomyData,Versions,Formats,Compliance,LifecycleData}.js`)

`ei_attachments` is the ONE canonical record per received file (no parallel documents table). Each STEP is optional: the worker probes for its columns (`documentRegisterReady` etc. in `outlook-sync`) and the pipeline only writes them when present. **STEP268** files every document: header data (`documentMeta`), workspace `area` + `primary_module` / `related_modules` (from the type, else `DOC_TYPE_MAPPING`), project via PO → `matchProject()` on email + document text; `project_status` MATCHED (≥ `settings.documents.auto_link_min`, default 0.8) / SUGGESTED / AMBIGUOUS / UNASSIGNED, `review_state` OK / NEEDS_TYPE / NEEDS_PROJECT / NEEDS_BOTH. Project members (assignments) see filed docs via `ei_project_documents()` + a storage policy; filing changes only via `ei_document_set_project` / `ei_document_set_type`. UI: Projects → Documents (`components/ei/DocumentFiling.jsx`), Email Intelligence → Document filing. **STEP269** taxonomy (≈600 types, 26 families, `eiTaxonomyData.js`, loaded into the draft config by `ei_import_taxonomy()` from the "Load baseline taxonomy" button) + `ei_acronyms` (one row per meaning, customer/project scope, context words; part of the versioned snapshot). `matchTaxonomy()` runs when no keyword rule fires; an acronym with several plausible meanings never decides a type (`resolveAcronym`). **STEP270** AI new-type suggestions (`normalizeSuggestion`, `ei_suggest_document_type`, `ei_type_suggestions`); approve / merge / reject in `TypeSuggestions.jsx` re-types the waiting files (`_ei_retype_suggested`) — never applied without a person. **STEP271** duplicates / revision chains (`relateDocument`: EXACT_DUPLICATE / NEW_REVISION / OLDER_REVISION auto-linked, SAME_REVISION / SIMILAR suggested), `version_group_id` + `is_current`, nothing deleted. **Phase 5** (no SQL): `eiFormats.js` — validated ZIP (count, size, ratio, paths, encryption), DOCX/PPTX/ODF/RTF/old DOC text, EML + Outlook item attachments (MIME via Graph `$value`) expanded one level into their own documents; password-protected / damaged files → SKIPPED + `DOCUMENT_REVIEW`. MSG and OCR-without-AI are not supported. **STEP272** lifecycle templates (government 16 stages, EPC, IT — `eiLifecycleData.js`) and per-project Document Compliance Register (`ComplianceRegister.jsx`, pure `evaluateRegister()`): required vs received, approvals / waivers / N/A recorded by a person only, statutory items, expiry from the item or the document's extracted `expiry_date`. Tests: `node --test src/lib/ei{Documents,Taxonomy,Discovery,Versions,Formats,Compliance}.test.mjs` (shared fixtures in `src/lib/eiFixtures.mjs`).

### Agreements & e-Sign (`sql/STEP273`, `src/lib/esign*.js`, `src/pages/AgreementsPage.jsx`, public `/sign/:token`)

Agreements, NDAs, MSAs, EPC contracts, SOWs, purchase orders and work orders: made from a template (built-ins in `esignTemplates.js`: `{{field}}` placeholders, `items` line-item field → `{{items_table}}` / `{{items_total}}`; org templates in `esign_templates`) or an uploaded PDF (`esign_files`, bytea ≤ 10 MB, via `esign_set_file`). Editable only while DRAFT (RLS + column grants); `esign_send()` freezes it and stores the SHA-256. Signers sign in order (SEQUENTIAL) or together (PARALLEL) on `/sign/<token>` (no login, `esign_public_*` RPCs; optional 6-digit email code, IP + browser recorded, `esign_events` audit trail). `esign_signers.token` is not selectable by the app — `esign_signing_link()` returns it to managers / the creator. Emails use the existing outbox template `notification` (no Edge Function deploy); internal signers get an in-app notification instead. The signed PDF (original + signature certificate) is built in the browser by `esignPdf.js` (jsPDF + pdf-lib). Team signers get `/agreements?id=<doc>&sign=1` and sign in an overlay inside the tab (`SigningView` / `SignPanel`, `esign_my_signing_token`, STEP274). "Open file" on an Email Intelligence document (`components/esign/OpenInAgreements.jsx`) opens it in the tab, creating an UPLOAD draft from the PDF once (`agreementFromAttachment`, `esign_documents.source_attachment_id` unique, STEP275); non-PDFs or users who can't create agreements just open the file. Run `node --test src/lib/esign.test.mjs`.
